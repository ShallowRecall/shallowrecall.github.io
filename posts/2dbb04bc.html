baoyu-translate实战：用术语表和审校流程翻译技术文章

发表于2026-10-15|更新于2026-10-15|技术笔记开发工具宝玉Skills
|阅读量:

返回总教程

baoyu-translate 的核心不是把英文逐句换成中文，而是把译文生产拆成可检查的步骤：先理解内容与术语，再翻译，必要时独立批评、修订和润色。尤其需要注意，它的命令行脚本主要负责 Markdown 分块，真正的翻译由 Agent 完成。

本文基于固定提交源码核对。案例为操作示例，不是付费翻译、在线模型或账号实测；撰写时未运行技能、安装依赖或生成实际译稿。

一、适用场景与能力边界

适合英文技术博客、产品说明、研究解读和需要统一术语的长文。输入可以是本地文件、粘贴文本或 URL。URL 输入仍需要先取得合法可访问的正文；翻译技能不能把登录墙后不存在于上下文中的内容“翻译出来”。

三种模式对应不同成本与质量目标：

模式 工作流程 适合场景
quick 直接翻译 短通知、理解一句话、非正式内容
normal 分析、组装提示、翻译 一般技术文章与博客
refined 分析、初稿、批评、修订、润色 需要公开发布或认真引用的稿件

“精翻”不等于事实验证，也不是专业领域认证。数字、因果、否定、条件和引用仍要对照原文。法律、医疗或合同类重要文件，应让相应专业人员复核，不能把语言自然当成内容可靠。

另一个边界是图片。技能可以提醒哪些图里仍有源语言文字，但不会默认重画、OCR 或翻译图片文字。文章中文化后，图中英文标签仍可能存在，需要单独决定是否处理。

需要具备读写文件能力的 Agent；长文分块依赖 Bun 或通过 npx -y bun 调用的 Bun。短文翻译主要是 Agent 工作流，不应误称必须先配置一个单独的翻译 API Key。

三、输入输出与中间文件

本地文件直接作为来源，不需要复制；粘贴文本或 URL 内容先落为 translate/{slug}.md。译文目录位于来源旁边，形态为 {原文件名}-{目标语言}/。目标语言代码应由 Agent 明确报告，不要把示例里的 zh 当作所有情况都使用的目录后缀。

所有模式最终都写 translation.md。普通模式还包含 01-analysis.md 与 02-prompt.md；精翻增加 03-draft.md、04-critique.md、05-revision.md。长文另有 chunks/ 保存原文分块和翻译分块。输出目录已经存在时，参考流程要求先重命名备份，再建立新目录，不能静默覆盖。

这些文件帮助定位错误：术语理解错误查分析，反复用错译名查共享提示，漏译查分块，润色偏离原意则对照初稿和批评。若只收到一个漂亮的最终文件，却没有请求模式要求的中间稿，工作流可能没有完整执行。

六、操作案例：翻译一篇长技术文章

假设本地有一篇约六千英文词的代理系统文章，包含代码、两张图片和重复出现的术语。目标是给团队做中文阅读材料。以下是工作流示例，不是已完成翻译的报告。

  1. 检查原文。 确认开头、中间、结尾齐全，代码围栏闭合，图片链接存在。来自网页时先验收采集结果，不能在残缺正文上讨论翻译质量。
  2. 先定全篇词表。 提取 Agent、tool call、context 等词，按语境确定译法。共享词表应在分块前生成，避免不同子任务各自决定术语。
  3. 按 Markdown 结构分块。 normal/refined 默认在四千词阈值触发分块，每块上限默认五千词；优先按块边界切分。极大单块仍可能退回行或词级切分，因此不能承诺任何代码块绝不会被拆。
  4. 翻译并有序合并。 有子 Agent 时每块使用相同共享提示与位置说明，无子 Agent 时顺序处理也可。合并按原始顺序，检查段落和标题没有重复、丢失。
  5. 独立批评与修订。 04-critique.md 只诊断，不伪装成另一份终稿。重点查数字、因果方向、语气强弱、术语漂移与中文不自然句式，再产出修订稿和最终稿。
  6. 检查双端使用。 Obsidian 中打开最终稿，检查图片相对路径。译文位于新子目录，原图未必跟着移动，不能保证自动可用。准备 Hexo 时保留来源、核对元数据并只发布最终稿，不把分析文件全送进博客。

七、长文与元数据的注意点

quick 模式不分块，即使原文很长也如此；超过阈值应提示用户换 normal，而不是暗中改变模式。分块能减少上下文压力，但不自动保证术语百分之百一致，最终仍需全篇搜索核心词。

原文 YAML 中的来源元数据会按规则改为 source 前缀，例如 url 到 sourceUrl，并添加译后字段；其他字段保留。若正文已有一级标题，规则可能不再新增顶层 title，所以 Hexo 发布前要检查站点实际需要的标题字段。不要让翻译流程覆盖自己既定的 slug 或把来源文章的发布日期误当成当前译稿发布日期。

译者解释应少量、明确，与作者原意区分。润色允许改善中文语序，但不能扩展论点、补充不存在的性能结论或替作者提高确定性。

八、验收与排错

  • [ ] 最终文件确实为 translation.md，模式要求的中间稿齐全。
  • [ ] 术语全篇一致，关键名称首次出现按需要保留原文。
  • [ ] 数字、单位、否定、条件、引用和代码未被改写含义。
  • [ ] 分块按顺序合并，原文段落没有缺漏或重复。
  • [ ] 旧输出已备份，图片与相对链接在新位置能打开。
  • [ ] 元数据适合 Obsidian 与 Hexo，只有最终稿进入发布范围。

命令执行后只有 chunks，没有译文。 这是分块脚本的真实职责，不是故障；需要 Agent继续翻译工作流。

术语表没生效。 检查命中的配置位置、外部词表相对路径与本次共享提示，不要只看某一处词表文件存在。

图片仍是英文。 这属于图片语言检查提醒范围，当前翻译步骤不会自动重做图片。

九、相关技能与固定来源

  • 网页转 Markdown：先取得完整来源。
  • YouTube 字幕提取：给翻译准备可追溯字幕。
  • Markdown 排版：译文确认后再整理展示。
  • Markdown 转 HTML：为已完成译文生成平台展示稿。
